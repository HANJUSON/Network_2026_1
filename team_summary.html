고빈도 거래(HFT) 시스템에서 TCP와 UDP 중 어떤 프로토콜이 지연시간 성능에 더 유리한가? 특히 패킷 손실 환경에서 두 프로토콜의 성능 차이가 어떻게 나타나는가?
왜 HFT인가?
고빈도 거래에서 1ms의 지연 차이가 수익과 손실을 결정합니다. 전송 계층 프로토콜 선택은 시스템 설계의 핵심 결정 중 하나이며, 이 프로젝트는 그 차이를 실측 데이터로 검증합니다.

왜 Docker 분리 환경이 필요한가
문제: 로컬 loopback (127.0.0.1)
같은 PC에서 loopback으로 측정하면 OS 커널이 NIC와 네트워크 스택을 우회합니다. 결과적으로 측정값이 "TCP vs UDP 차이"가 아닌 "Python 소켓 API 호출 오버헤드"에 가깝고, tc netem 같은 네트워크 조건 주입도 적용되지 않습니다.
해결: Docker bridge 네트워크
두 컨테이너가 별도 가상 이더넷 인터페이스(veth pair)를 통해 통신하므로 실제 네트워크 스택을 경유합니다. 서버 컨테이너의 eth0에 tc netem을 적용하여 지연·손실·지터를 수치로 정밀 제어할 수 있습니다.

핵심 인사이트 — TCP P99가 204ms까지 폭등하는 이유
TCP 재전송 타이머 (RTO) 메커니즘
패킷이 손실되면 TCP는 수신 확인(ACK)을 기다리다 타임아웃 후 재전송합니다. Linux 커널의 RTO(Retransmission Timeout) 최솟값은 200ms입니다.

따라서 재전송이 발생한 주문은 반드시 200ms 이상의 지연을 겪습니다. 손실률 1%이면 1,000개 중 ~10개가 해당하고, P99(하위에서 990번째)가 바로 이 재전송 구간에 걸립니다.

결과: 375μs → 204,812μs (545배)
UDP의 대응 방식
UDP는 재전송 메커니즘이 없으므로 손실된 패킷은 그냥 포기됩니다. 생존한 992개의 주문은 손실 전과 동일한 지연시간을 유지합니다.

트레이드오프
· TCP: 손실 0개, P99 = 205ms
· UDP: 손실 8개, P99 = 374μs

HFT 관점에서 "주문 8개 포기" vs "10개 주문에 200ms 지연" 중 어느 쪽이 더 큰 손실인지는 거래 전략에 따라 다릅니다.

실제 HFT 시스템과의 차이 및 시사점
실제 HFT 시스템의 선택
실제 금융 거래소(NYSE, CME 등)는 UDP 기반 멀티캐스트로 시세 데이터를 배포하고, 주문 전송은 TCP + 커널 바이패스(DPDK, RDMA)를 혼용합니다.

커널 TCP의 RTO 200ms 문제를 피하기 위해 자체 재전송 로직을 응용 계층에서 구현하거나, FPGA를 사용해 TCP 스택 자체를 하드웨어에 구현합니다.
이 프로젝트의 한계 & 의의
한계: 실제 HFT는 μs~ns 단위 커널 바이패스, FPGA, 전용 광섬유를 사용하지만 본 구현은 Python 소켓 API 기반이므로 절대 수치는 차이가 큽니다.

의의: 프로토콜 간 상대적 특성 차이 — 특히 패킷 손실 환경에서 TCP RTO가 초래하는 P99 폭등 현상 — 은 실제 환경과 동일한 메커니즘으로 재현됩니다.
결론
1. 이상적 환경(손실 없음): TCP와 UDP의 지연시간 차이는 평균 ~10μs로 실질적으로 무의미합니다.

2. 패킷 손실 1% 환경: TCP P99가 375μs → 204ms (545배)로 폭등합니다. 원인은 Linux 커널 RTO 최솟값 200ms — 손실 발생 주문은 반드시 200ms 이상 지연됩니다. UDP는 동일 조건에서 P99 374μs를 유지하지만 8개 주문을 잃습니다.

3. 핵심 트레이드오프: 신뢰성(TCP) vs 예측 가능한 지연시간(UDP). HFT 시스템에서 "주문 1개 손실"이 "해당 주문 200ms 지연"보다 나은 경우가 많아 실무에서는 UDP + 응용 계층 재전송 혼합 방식을 채택합니다.

4. 결론: 패킷 손실이 있는 환경에서는 UDP가 지연시간 관점에서 압도적으로 유리하며, 이것이 HFT 인프라에서 프로토콜 선택이 중요한 이유입니다.
